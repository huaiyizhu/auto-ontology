# 运行、配置与数据初始化

先阅读[项目说明](./README.md)。以下以当前本地 Compose + Azure 模型试用为例；正式 Kubernetes 安装以 [DEPLOYMENT.md](../../DEPLOYMENT.md) 为准。

## 1. 准备环境

- Docker Desktop / Docker Compose v2，能够拉取镜像和访问 Ubuntu、Node、Python 软件源。
- `uv`，用于本机执行 Python 工具；准备依赖执行 `uv sync`。`--no-sync` 仅适合依赖已安装的环境。
- 有效聊天模型部署、Embedding 部署和认证信息；当前使用 Azure DeepSeek 与 Cohere `embed-v-4-0`。
- 管理员邮箱、密码及随机认证密钥。应用不开放自助注册。

已有 `.env` 时直接编辑，不要用示例覆盖实际配置。首次才执行 `cp .env.example .env`。
密钥写入本地文件，不提交 Git，也不贴进日志或聊天。

## 2. 填写 `.env`

```dotenv
POSTGRES_HOST=localhost
POSTGRES_PORT=5433
POSTGRES_USER=postgres
POSTGRES_PASSWORD=<Docker数据库密码>
POSTGRES_DATABASE=auto_ontology

PGADMIN_EMAIL=admin@example.com
PGADMIN_PASSWORD=<pgAdmin密码>
APP_URL=http://localhost:3000
AUTO_ONTOLOGY_ADMIN_EMAIL=admin@example.com
AUTO_ONTOLOGY_ADMIN_PASSWORD=<应用管理员密码>
AUTH_SECRET=<至少32字符的随机字符串>

DEFAULT_MODELS_API_KEY=<Azure聊天模型Key>
DEFAULT_MODELS_ENDPOINT=https://<资源>.openai.azure.com/openai/v1
DEFAULT_MODELS_MODEL=<实际聊天部署名>

EMBED_API_KEY=<Azure向量模型Key>
EMBED_ENDPOINT=https://<资源>.services.ai.azure.com/openai/v1
EMBED_MODEL=embed-v-4-0
EMBED_API_STYLE=azure-cohere
EMBED_VECTOR_SIZE=1536
```

Endpoint 和部署名以实际 Azure 调用示例为准。1536 是本次实际响应维度，不能套到所有模型。
切换向量模型或维度时，旧向量不能直接继续使用，需要有计划地重建索引；仅改变量不会迁移已有向量列。

`REASONING_*`、`NON_REASONING_*` 每个字段均可继承 `DEFAULT_MODELS_*`。
示例中显式设置的占位 Key 会覆盖默认 Key，需要删除、注释或替换。
`RERANK_*` 注释后同样继承默认值，**不会关闭重排**；聊天模型不能替代 rerank 服务。

## 3. 先启动数据库并初始化示例业务数据

```bash
docker compose up -d postgres
uv sync
uv run --no-sync python -m dev_tools.fixtures.seed_fixtures
```

脚本会创建 `pagila`、导入 `pagila.sql` 和 `pagila_analytics.sql`，并生成 `chinook.sqlite`。
`pagila` 已有 sentinel 表时会跳过导入；SQLite 已有目标表时同样跳过。这不是任意部分导入失败后的通用修复机制。

源文件及说明见 [fixtures README](../../dev_tools/fixtures/sql/README.md)。Pagila 是固定版本的裁剪样本，不是完整生产数据。

数据库账号至少需要创建示例库的权限；当前使用 Docker 初始化账号。
修改 `.env` 的用户或密码不会更改已经初始化的数据卷中的账号。

## 4. 配置本机与容器的数据源

下面两行都是模板，账号密码需要 URL 编码，路径替换成自己的绝对路径。

```dotenv
# 本机运行 fixture 工具时使用
CONNECTION_STRINGS=postgresql://<用户>:<URL编码密码>@localhost:5433/pagila,sqlite:////<绝对路径>/dev_tools/fixtures/sql/chinook.sqlite

# Docker 后端及 ingestion-service 使用
DOCKER_CONNECTION_STRINGS=postgresql://<用户>:<URL编码密码>@postgres:5432/pagila,sqlite:////fixtures/chinook.sqlite
```

SQLite 的绝对路径 URL 是 `sqlite:///` 加 `/开头的绝对路径`，即共四个 `/`。
Compose 已将 `./dev_tools/fixtures/sql` 只读挂载为 `/fixtures`。

| 运行位置 | Docker PostgreSQL 地址 | SQLite 路径 |
| --- | --- | --- |
| Mac 本机工具 / 数据库客户端 | localhost:5433 | 仓库内实际绝对路径 |
| Compose 内部服务 | postgres:5432 | /fixtures/chinook.sqlite |

如果源库确实在 Mac 本机，容器通常用 `host.docker.internal:<本机端口>`。
不能把容器内 `localhost` 当成宿主机。

UI-managed Connections 一旦存在，环境变量中的连接集合不再作为数据源使用。
修改 `.env` 却没有效果时，先检查 Settings → Connections 中是否已有连接。

## 5. 启动全栈与应用迁移

```bash
docker compose up -d --build
docker compose ps -a
docker compose logs --tail 80 auto-ontology-migrate frontend-migrate
```

- `auto-ontology-migrate`：Alembic 初始化内部 `public` 目录和语义层表。
- `frontend-migrate`：Prisma 同步 `frontend` 用户、会话、OAuth 等表。
- 向量表由向量存储写入路径按需创建于 `vdb` Schema。
- 迁移任务成功后退出属于正常情况，长期运行的应用服务应保持运行。

访问 http://localhost:3000，用 `AUTO_ONTOLOGY_ADMIN_*` 登录。
`dev_tools/setup_env.sh` 无参数也会启动全栈；其 `--dev` / `--ds` 模式供修改项目代码的开发者使用，不是首次试用的必要步骤。

## 6. 选择语义层初始化路线

### A. 固定 fixture 语义层

```bash
uv run --no-sync python -m dev_tools.fixtures.seed_graph_fixture --reset
```

**该命令会清空已有目录、语义层和相关向量，然后写入测试模型。仅对可重建的 Demo 环境使用。**
它读取配置的源库、创建目录，并写入手工定义的术语、列属性、SQL 属性、分析和 zones。
它特意跳过 Embedding，适用于确定性测试；执行成功并不代表问数检索已就绪。

本次试用另外使用现有 `_build_rows`、`batch_embed`、`write_embedded_rows`、SQL Attribute 和 CustomAnalysis 的服务方法补建了语义索引，保留了每条记录的 `database_name`。
这是一次性调试脚本，不是仓库提供的固定 CLI；不要依赖 `/tmp` 脚本作为长期安装步骤。

要在新环境复用已审阅的模型，可先从当前环境导出 YAML，在隔离环境通过 Import / Export 导入并开启 `embed`，随后验证索引和数据源；见[模型导出说明](./Demo与模型导出.md)。导入前备份，确认 replace 范围。

### B. 真实数据源与自动编译

在 Settings → Connections 添加源库、测试连接并保存。保存成功不代表采集或编译已经完成。
确认目录出现预期的数据库和表，再检查语义编译状态，按界面执行所需编译操作。
自动编译使用模型推断语义，结果需人工核对。

可通过已认证的 Web API 检查 `GET /api/semantic-compilation/status`。
不要为了“重试”随意调用 `/api/semantic-compilation/reset`，它会破坏性重建已编译层。
UI 数据源测试与保存操作分别是 `/api/connections/test` 和 `/api/connections`；权限见 OpenAPI。

## 7. 数据库客户端连接

```bash
psql -h localhost -p 5433 -U postgres -d pagila -W
```

密码来自本地 `.env` 的 `POSTGRES_PASSWORD`，不是应用管理员密码，也不是模型 Key。
内部应用库使用相同地址和账号，数据库名改为 `auto_ontology`。

## 8. 排障速查

| 现象 | 原因 / 检查 |
| --- | --- |
| `KeyError: POSTGRES_USER` | 脚本未加载 `.env` 或文件未设置；当前两个 fixture 入口已修复 |
| `role postgres does not exist` | 很可能连到了 Mac 本机 5432；检查 Docker 映射 5433 |
| 迁移认证失败 | 现有数据卷账号与 `.env` 不一致；保留数据并修正凭据，不靠重建卷解决 |
| Docker 内数据源连接超时 | 使用了 localhost，或容器仍持有旧环境；核对 DOCKER_CONNECTION_STRINGS 并重新创建服务 |
| SQLite 找不到 | 宿主机路径不能直接在容器里用；检查只读挂载 |
| Azure Embedding 404 | 核对 `/openai/v1` 基址和真实部署名 |
| Azure 提示不支持 truncate | 核对 EMBED_API_STYLE=azure-cohere 和正在运行的镜像版本 |
| 向量维度错误 | 模型实际输出、配置、已有表向量维度不一致 |
| prepare_candidates 校验失败 | 检查先前 Embedding 错误、语义索引条数、数据库作用域和权限，不直接绕过校验 |
| Ubuntu 软件包下载失败 | Docker 构建网络、代理或软件源问题，与模型 Key 无关 |

修改运行时 `.env` 后执行 `docker compose up -d` 使容器使用新配置；修改 Python 源码后使用 `--build`。
停止服务可用 `docker compose down`；`down -v` 会删除数据卷，不作为常规排障步骤。

## 附录：固定 fixture 的一次性语义索引补建

以下是本次试用的补建方式，调用内部 Python API，不是稳定产品 CLI。仅用于上述两个测试库。它会将术语、字段说明、SQL 和分析内容发送给配置的 Embedding 服务；确认授权、备份及数据源后执行。索引已有其他模型维度时，先制定迁移方案，不要直接覆盖。

将下列内容保存到仓库根目录临时文件 `reembed_demo.py`，运行 `uv run --no-sync python reembed_demo.py`，完成后删除临时文件。清除代理环境变量仅影响该 Python 进程；需要代理访问 Azure 时按本机环境调整。

```python
from dotenv import load_dotenv
load_dotenv('.env')
import os
for k in ('ALL_PROXY','HTTPS_PROXY','HTTP_PROXY','all_proxy','https_proxy','http_proxy'): os.environ.pop(k,None)
from auto_ontology.dal.terms import fetch_all_terms_and_attributes
from auto_ontology.dal.datasources import fetch_schemas_by_ids
from auto_ontology.semantic.embed import _build_rows
from auto_ontology.utils.embedding import batch_embed,get_embed_params
from auto_ontology.vdb import get_semantic_vdb
from auto_ontology.vdb.records import write_embedded_rows
terms,attrs=fetch_all_terms_and_attributes()
tables={r['table_id']:r['database_name'] for r in fetch_schemas_by_ids()}
rows=[]
for t in terms:
 a=[a for a in attrs if a.get('term_name')==t['name']]
 for db in sorted({tables[x['table_id']] for x in a}):
  rows.extend(_build_rows(db,t,[x for x in a if tables[x['table_id']]==db]))
print('Embedding semantic rows:',len(rows),flush=True)
vdb=get_semantic_vdb()
print('Written:',write_embedded_rows(vdb,batch_embed(rows,get_embed_params())),flush=True)
from auto_ontology.dal.sql_attributes import list_sql_attributes,fetch_tables_from_sql_attributes
from auto_ontology.server.sql_attributes.service import _embed_sql_attribute
for a in list_sql_attributes():
 dbs={t['database_name'] for t in fetch_tables_from_sql_attributes([a['id']])}
 for db in dbs:_embed_sql_attribute(get_embed_params(),vdb,a['id'],db)
from auto_ontology.dal.custom_analyses import list_custom_analyses
from auto_ontology.server.custom_analyses.service import _embed_analysis
for a in list_custom_analyses():_embed_analysis(a['id'])
from auto_ontology.utils.retriever import get_semantic_objects_retriever
for q in ('国家','销售额'):
 hits=get_semantic_objects_retriever().query(q,top_k=3)
 print('Semantic search:',q,'hits:',len(hits),flush=True)
```

完成后按 Demo 文档检查实际条数和候选，不能仅凭脚本退出码判断问数已完全可用。
